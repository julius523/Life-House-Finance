# Life House Reentry Open-Source Finance Stack

## Comprehensive Implementation Guide for Replit or Manus AI

## 1. Objective

Build a branded, low-cost, implementation-ready finance operations stack for Life House Reentry that supports:

* organizational expense reporting
* receipt tracking and OCR
* document retention and audit readiness
* bank transaction import and reconciliation
* GAAP-style accounting workflows
* program / grant / fund / site reporting
* approval workflows for reimbursements and vendor spending
* clean month-end close processes
* future automation without locking the organization into expensive software

This guide is written so it can be handed directly to Replit or Manus AI as a build spec.

---

## 2. Recommended Strategy

### Core Decision

Use **one primary accounting system**, **one receipt/document system**, and **one bank-ingestion method**.

### Recommended Stack

#### Required

1. **ERPNext** → core accounting, expense approvals, reimbursements, vendor bills, reporting, dimensions, budgets, reconciliations
2. **Paperless-ngx** → OCR, searchable receipt storage, bank statement storage, invoice storage, document tagging, audit trail
3. **PostgreSQL / MariaDB / Redis** → databases and caching required by the core apps
4. **Docker Compose** → simplest low-cost deployment and maintenance path
5. **Caddy or Traefik** → free HTTPS with automatic certificates

#### Optional Later

6. **Actual Budget** → optional cash-monitoring or departmental budgeting sidecar, not system of record
7. **Custom integration microservice** → sync helper between Paperless and ERPNext, webhook listener, import parser, notification service
8. **MinIO or S3-compatible storage** → optional object storage for backups and attachments
9. **Metabase or Apache Superset** → optional advanced dashboards

### What We Are Not Doing

* We are **not** running multiple accounting ledgers in parallel.
* We are **not** making Firefly III or Actual Budget the official accounting system.
* We are **not** depending on paid AI APIs to make the core stack work.
* We are **not** requiring live bank sync in phase 1.

### Why

This keeps the system:

* cheap
* auditable
* easier to maintain
* easier to train staff on
* less likely to create duplicate transactions or broken reconciliations

## 8. Important Truths Before Building

1. **GAAP-level accounting is not created by software alone.**
2. You must define chart of accounts, approval rules, reconciliations, close procedures, document retention, and access controls.
3. The open-source stack should support the workflow, not replace accounting judgment.
4. The biggest risk is bad configuration, not lack of features.
5. Manual bank import in phase 1 is smarter than unstable auto-sync.

## 18. Receipt Workflow

### Phase 1 Workflow

1. user uploads receipt to Paperless intake inbox
2. Paperless OCRs and tags the document
3. finance or user creates expense claim in ERPNext
4. ERPNext record stores the Paperless document ID or URL reference
5. approver reviews
6. finance reviews coding and completeness
7. accounting posts transaction
8. bank import later matches the outgoing payment or card transaction
9. month-end report flags any expense with missing documentation

```text
YYYY-MM-DD_VENDOR_AMOUNT_CATEGORY_REQUESTOR
```

## 19. Bank Import Workflow

### Strategy

Use a layered approach:

1. **Phase 1 live-ish and free:** ingest transaction notification emails from Google Workspace and parse them into a staging table
2. **Phase 1 accounting truth:** continue to support manual CSV / OFX / QFX imports for reconciliation accuracy
3. **Phase 2 optional:** add direct bank sync provider only if it proves stable, secure, and worth the cost

### Email-Based Transaction Tracking

If the bank sends transaction emails or alerts:

* create a dedicated mailbox such as `bankfeeds@lifehousereentry.com`
* auto-forward transaction alerts there
* parse sender, subject, timestamp, merchant, amount, masked account, and transaction type
* create a staged bank event record
* match staged records later against formal statement imports
* never treat email alerts as the final accounting record by themselves

### Why This Matters

Email alerts can provide near-live visibility while manual imports remain the source used for final reconciliation and month-end accuracy.

### Phase 1 = Manual Import

Support import of:

* CSV
* OFX
* QFX

### Normalization Rules

The import parser should normalize to a standard schema:

* transaction_id
* account_name
* posting_date
* description
* amount
* direction
* balance
* source_file
* raw_hash
* source_type (`statement_import`, `email_alert`, `manual_entry`)

### Dedupe Rule

A transaction is duplicate if:

* same account
* same date
* same absolute amount
* same normalized description OR same bank transaction id

### Match Rule Priority

1. exact reference / check number / transfer id
2. exact amount + date window + vendor name similarity
3. exact amount + same employee reimbursement batch
4. email alert matched to later statement line
5. manual review queue

### Security Rule

Do not hard-code bank account or routing details into app source, prompts, public docs, or front-end code. Store any bank metadata only in encrypted admin settings or secure secrets where absolutely necessary.
