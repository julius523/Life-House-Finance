That is the right next dependency. Reporting can wait a beat.

Why:

Expenses are now bridged. Bills are the other major operational stream still sitting outside the accounting control path.
If you do reporting first, you polish outputs while a core input is still missing.

Use this as the full planning prompt in one place:

Bills → accounting bridge (draft JE, not direct post)
What & Why

Expenses are now connected to accounting through the controlled draft → submit → approve → reject → post workflow, using the shared accounting_source_links bridge and the existing hardened manual journal entry controls. Bills are the next operational accounting gap.

This task connects bills into the same accounting control layer. When a bill reaches the configured accounting trigger, the server should generate a manual journal entry draft, not a posted ledger row. That draft must then flow through the existing draft approval workflow unchanged. No bypass route, no silent posting, no second posting implementation.

Bills differ from expenses because they have an A/P lifecycle:

At accrual/approval: Dr expense, Cr accounts payable
At payment: Dr accounts payable, Cr cash

This work should use the same accounting_source_links table so bills plug into the same traceability model as expenses, and so later reporting and copilot reconciliation can read one canonical source of truth.

Done looks like
Bills can generate accounting drafts using the shared accounting_source_links table with sourceType='bill'.
The system creates draft JEs, not posted JEs.
Generated bill drafts use the existing manual JE workflow: draft → submit → approve → reject → post.
No second posting path is introduced. Any eventual posting must reuse the hardened posting service already used by manual drafts.
The accrual event creates a draft with:
Debit: bill expense account
Credit: accounts payable liability account
The payment event creates a draft with:
Debit: accounts payable liability account
Credit: cash / bank account
The bridge is idempotent:
same bill + same accounting event cannot create duplicate drafts
retries and concurrent calls converge on the same draft/link row
Mapping failures do not block operational bill approval/payment. They set accounting status to blocked with a stable reason code and leave an audit trail.
Bills get the same accounting status model as expenses where applicable:
pending | draft_created | posted | blocked | not_applicable
Blocked bill generation is visible and retryable through the same overall pattern already used for blocked expenses, whether by extending the queue or creating a bill-specific companion queue.
Two-way traceability exists:
bill detail links to draft / posted JE
JE detail can show originating bill
all traversals go through accounting_source_links
Audit history is preserved:
generation attempt
blocked reason
retry
mark not applicable
eventual posted linkage
Locked design constraints
Use the existing shared bridge table: accounting_source_links
Do not put ad hoc source fields directly on journal entries or drafts as the canonical bridge
Do not direct-post to the ledger from the bill workflow
Do not create a new JE posting implementation
Reuse the existing manual draft workflow and hardened posting path
Keep the server as the source of truth for all validations, even if the UI filters options
Preserve the audit chain; never “clean up” by deleting linkage rows that would sever provenance
Accounting model
1) Bill accrual / approval event

When a bill reaches the configured accrual trigger, generate one draft JE:

Dr expense account
Cr accounts payable liability account

Suggested default trigger for v1:

on bill approval
2) Bill payment event

When a bill is actually paid, generate a second draft JE:

Dr accounts payable liability account
Cr cash / bank account

If the current bill system does not yet have a reliable payment event/state, plan this as either:

part of the same task if the payment state already exists and is stable, or
a tightly-coupled follow-up slice if payment tracking is not ready

But the planning doc must explicitly account for both sides of the A/P lifecycle.
