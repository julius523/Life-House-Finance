Acceptance criteria

A. Reconciliation backend gains per-entry integrity checks
Add a new reconciliation section focused on individual posted journal entries in the selected range.

Checks to include:
1. Every posted/reversed journal entry is balanced to the cent.
   - Per entry: sum(debits) == sum(credits)
   - Return failing entry ids/numbers and the delta in cents.
2. No journal-entry line is missing a valid chart_of_accounts reference.
   - If accountId is null, missing, or points to a non-existent account, fail it.
3. Optional but preferred if cheap from current schema:
   - No entry has zero lines.
   - No line has a zero/negative invalid amount shape if your schema permits malformed legacy rows.
Only include checks that can actually fail and are not tautologies of the current query shape.

API requirements:
- Extend GET /reports/reconciliation.
- Preserve existing response fields.
- Add a machine-readable perEntry section.
- Include:
  - totalEntriesChecked
  - failingEntryCount
  - failingEntries[] with:
    - journalEntryId
    - entryNumber
    - entryDate
    - checkCode
    - status
    - deltaCents where relevant
    - shortMessage
- Keep admin/approver auth exactly as today.

Important:
- Use the same posted/reversed status semantics and entry_date filters as the rest of ledger reporting.
- Do not create a second source of truth. Reuse existing helper/query patterns where possible.

B. Reconciliation UI surfaces the failing entries clearly
On the Reports page reconciliation card:
- Keep the current overall pass/fail summary.
- Add a “Per-entry integrity” subsection.
- Show:
  - total entries checked
  - failing count
  - pass/fail badge
- If failures exist, render a compact table/list of failing entries with:
  - entry number (linked to JE detail)
  - date
  - failed check
  - delta if applicable
  - short explanation
- If no failures, show a clean “All journal entries balanced and mapped” state.

UI rules:
- Ledger mode only, same as the current reconciliation card.
- No noisy wall of data; cap initial visible failures at a reasonable number like 25 with a “show more” affordance if needed.
- Use typed hooks only.
- Keep the card resilient: if the per-entry subsection errors, it must not white-screen the page.
