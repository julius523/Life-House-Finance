Expense → Accounting Bridge, Phase 1
Tasks #51, #52, #53, #54 — Mapping foundation, auto-generated draft bridge, traceability, and blocked queue
What & Why

The accounting workflow is now real: Chart of Accounts, manual JE drafts, submit/approve/reject/post, no-self-approval, optimistic locking, idempotent posting, audit history, and approval history on posted JEs all exist.

But the accounting side is still not integrated with expenses.

Today, expenses are operational records only. They do not deterministically map to ledger accounts, they do not generate accounting drafts, they do not surface accounting blockages, and there is no clean UI traceability from an expense to its draft or posted JE and back again.

This phase creates the first real bridge from operations into accounting, without bypassing controls.

The bridge must work like this:

Finance defines expense categories and maps each category to the correct Chart of Accounts debit account plus payment-method-specific credit rules.
When an expense is approved, the server attempts to generate exactly one manual journal entry draft from that expense.
The generated draft is not auto-submitted and not auto-posted. It enters the existing draft workflow and must still be reviewed, submitted, approved, and posted through the existing accounting controls.
If generation fails because configuration is missing or invalid, the expense is marked accounting blocked and appears in a dedicated blocked queue for finance to fix and retry.
The system must expose two-way traceability so a reviewer can move in one click between:
expense
generated draft
posted journal entry

This is the keystone that makes later accounting/reporting work possible.

Non-negotiable design decisions

These are locked for this phase:

Trigger: generate the accounting draft when the expense transitions to approved
No silent posting: approval generates a draft only, never a posted JE
No auto-submit: generated drafts remain in draft status until a human reviews and submits them
Reuse the existing manual JE workflow: submit/approve/reject/post stays unchanged and must apply to generated drafts exactly as it does to hand-typed manual drafts
Reuse the existing posting path: when an expense-generated draft is eventually posted, it must still flow through the existing hardened posting service and idempotency path
Use a link table, not scattered foreign keys: create a shared accounting-link layer that can support expenses now and bills next
Single-tenant only: no organization_id work in this phase
No bill automation yet: bills are explicitly out of scope for this phase
No report cutover yet: this phase builds the bridge, not the final report migration
Done looks like
Mapping foundation
Admins can open a new expense category mapping page and manage expense categories.
Each expense category has:
a unique name
an active/inactive flag
a default debit account from the live Chart of Accounts
one or more payment-method-specific credit rules
at least one default credit rule
Only active CoA accounts that allow manual posting can be selected.
Archived, inactive, or non-manual-postable accounts are rejected server-side and filtered out of the UI.
The mapping page includes a “Categories without complete mappings” banner/report.
Expense form integration
Expenses gain a nullable categoryId.
Existing expenses are backfilled to a seeded Uncategorized category.
New expenses require a category.
Legacy expenses can remain uncategorized until edited, but show an explicit Uncategorized badge.
Draft generation
When an expense transitions to approved, the system attempts to generate exactly one manual journal entry draft.
The generated draft:
has status='draft'
has sourceType='expense'
has sourceId=<expense.id>
has deterministic memo / entry date / lines derived from the expense
Re-approving or retrying the same expense must not create duplicate drafts.
If generation cannot happen, the expense is marked accountingStatus='blocked' with a stable structured reason code and no draft is created.
Operational approval still succeeds even if accounting generation is blocked.

Hard acceptance gates

This phase is not complete unless all of the following are true:

An approved expense can generate at most one accounting draft.
Re-approval, retries, and retry storms do not create duplicate drafts.
Generated drafts remain in draft status and are not auto-submitted.
Generated drafts use the existing manual JE workflow and later post through the existing hardened posting path, not a second posting implementation.
If mapping is missing or invalid, the expense becomes accountingStatus='blocked' with a stable reason code and no draft is created.
Expense detail, draft detail, and posted JE detail all expose the linkage cleanly.
The blocked queue can retry successfully after mappings are fixed.
All write actions are audit-logged with actor and entity linkage.
Previously accepted accounting suites remain green.
Bills are untouched except for any shared link-table design needed to avoid rework later.
Out of scope
Bills auto-generation / AP accrual logic
Cash-basis on-payment trigger
Auto-submit of generated drafts
Auto-posting of generated drafts
Per-vendor overrides
Per-program overrides
Auto-retry on mapping changes
Report cutover to ledger-only

Multi-tenant scoping
Slack/email notifications for blocked queue growth
Locked data model decisions
1) Use an accounting link table

Do not scatter ad hoc link fields everywhere if a shared link model avoids rework.

Create a shared table for accounting-origin traceability, shaped so it can support expenses now and bills later. It should link a source entity to:

manual journal entry draft
posted journal entry

Recommended shape:

accounting_source_links
id
sourceType (expense now; room for bill later)
sourceId
manualJournalEntryDraftId
journalEntryId
timestamps
actor fields if useful
unique index on (sourceType, sourceId)

This becomes the canonical bridge instead of inventing separate one-off patterns for expenses and then bills.

2) Generated drafts are still manual drafts

Generated expense drafts are not a special new workflow type. They are standard manual journal entry drafts with:

sourceType='expense'
sourceId=<expense.id>

All existing workflow controls must apply unchanged.

3) Idempotency model

Use deterministic idempotency for generation, parallel to the existing posting idempotency model.

Recommended deterministic key:

expense-draft-<expenseId>

DB uniqueness must enforce this at the source-link / draft generation layer so retries and parallel attempts converge safely.

4) Account selection rules

Any referenced CoA account must be:

active
manual-postable

Server must validate this even if UI filters correctly.

Implementation order

Build in this order. Do not collapse this into one giant blob without respecting dependencies.

Task #52 — Generate accounting draft from approved expense
What & Why

Once an expense is approved, the system should create a manual JE draft so accounting controls govern every ledger hit. No silent posting.

Done looks like
Expense approval triggers draft generation attempt.
Exactly one draft is created per expense.
Draft has:
status='draft'
sourceType='expense'
sourceId=<expense.id>
Draft lines:
debit = category debit account
credit = payment-method rule credit account
both lines carry programId
Memo is deterministic:
merchant + description + expense ref
Entry date = expenseDate
Retry/re-approval does not duplicate drafts.
Mapping failure sets accountingStatus='blocked' and stable block reason.
Expense approval still succeeds even if accounting generation blocks.
Activity log written on both sides.
Locked behavior
Do not auto-submit
Do not auto-post
Do not backfill legacy approved expenses in v1
only new approvals trigger generation
manual retry endpoint exists for later reruns after mapping fixes
