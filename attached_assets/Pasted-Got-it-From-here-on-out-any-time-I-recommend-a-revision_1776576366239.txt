#63 - Bills → accounting bridge (draft JE, A/P split)

What & Why

Bills must enter accounting through the same controlled draft journal-entry workflow already used for manual journal entries and approved expenses. Bills create two separate accounting events that must stay distinct, traceable, and idempotent:

Accrual on bill approval
Dr Expense
Cr Accounts Payable
Payment on actual payment / linked transaction
Dr Accounts Payable
Cr Cash/Bank

This task extends the existing accounting bridge using the shared accounting_source_links table so bills can generate draft journal entries with full provenance, blocked-state handling, retry, and later posting through the existing hardened manual JE workflow.

Bills must never post directly to the ledger. This task creates drafts only. Submit → approve → reject → post continues to run through the existing manual JE approval workflow.

Done looks like
Approving a bill generates exactly one accrual manual journal-entry draft.
Paying a bill through a linked transaction generates exactly one payment manual journal-entry draft.
Both generated drafts are ordinary manual_journal_entry_drafts rows, not a special workflow type.
Both bill accounting events use the shared accounting_source_links table as the canonical provenance bridge.
accounting_source_links gains an eventType column so one bill can produce two distinct accounting links:
accrual
payment
Existing expense links are backfilled to eventType='primary'.
Database uniqueness is enforced on (sourceType, sourceId, eventType) so retries, repeated approvals, repeated payment triggers, and concurrency storms cannot create duplicates.
Bills gain split accounting-state fields so accrual and payment stay independently trackable:
accrualAccountingStatus
accrualAccountingBlockReason
accrualAccountingGeneratedAt
paymentAccountingStatus
paymentAccountingBlockReason
paymentAccountingGeneratedAt
Bills gain categoryId so the debit side of accrual resolves from the existing expense category → CoA mapping.
accounting_settings contains:
defaultApAccountId
defaultCashAccountId
Accrual generation uses:
debit = bill category’s mapped debit account
credit = defaultApAccountId
Payment generation uses:
debit = defaultApAccountId
credit = linked transaction’s CoA account if present, else defaultCashAccountId
If accounting generation fails, the operational bill transition still succeeds, but the accounting side is marked blocked with a stable reason code and no draft is created.
Admins/approvers can manually retry either event:
POST /bills/:id/regenerate-accounting-draft?eventType=accrual|payment
Admins/approvers can mark either event not applicable with a required note:
POST /bills/:id/mark-accounting-not-applicable?eventType=accrual|payment
Bill detail shows both accounting tracks with statuses, linked draft/JE summaries, block reasons, and action links.
Draft detail and posted JE detail show an Originating bill card when the source link points to a bill.
JE list distinguishes:
Manual
Expense #N
Bill #N (Accrual)
Bill #N (Payment)
The blocked accounting queue is generalized so blocked bill events appear alongside blocked expense events.
All bill accounting generation, block, retry, and not-applicable actions write stable audit-log rows.
Out of scope
Direct posting from bill workflows
Any bill-only shortcut that writes directly to journal_entries
Copilot reconciliation
Reporting polish / report drilldowns / CSV work
Vendor-specific smart rules beyond one category per bill
Full A/P sub-ledger redesign
Multi-currency or multi-entity support
Backfill of already-approved or already-paid legacy bills
Splitting one bill across multiple accounting categories
Auto-posting generated bill drafts
